The problem

Required 1 Concept Summary

One live model of stock, suppliers and orders — that hands over a decision, not a dashboard.

Ingest

CSV, manual entry, or API. Setup takes about two minutes and needs no IT project — because an SME that needs an integration project will never start.

Predict

Supplier signals are evaluated against the twin. Every alert carries a confidence score and a rationale written in the owner's language.

Act

An alternative supplier and a numbered plan. The owner accepts, adjusts or dismisses. Nothing happens without them.

04
What makes it trustworthy

Three decisions we would defend in front of a regulator.

The AI doesn't set the guarantees

The 48-hour floor and the sourcing priority are ordinary code with tests around them. A model that drifts changes the wording of an alert — it cannot change how early the alert fires.

The database enforces isolation

PostgreSQL row-level security, forced, under a non-superuser role. Missing tenant context returns zero rows, never every row. It fails closed.

It shows what it got wrong

Every warning is listed, including the ones that came to nothing. An owner who cannot see the misses has no basis for trusting the hits.

At 40,000 SMEs on shared infrastructure, an application-layer tenant check is one forgotten WHERE clause away from a breach. That is why this one lives in the database.

05
Required 2 Integration Plan

API-first, contract-first — and du already has the relationship.

Three ingestion paths, by SME maturity

  • CSV upload — businesses running on spreadsheets, which is most of them
  • Manual entry — the smallest, with a handful of SKUs
  • REST + webhooks — anyone with a POS or accounting system

The OpenAPI 3 contract is the source of truth, lives in the repository and is served at /docs. A test parses it on every commit.

Where it meets du

  • Identity — du SSO replaces the onboarding module without touching the twin
  • Distribution — the pilot cohort is a segment query, not a campaign
  • Notification — du's SMS or WhatsApp gateway is a provider, not a redesign
  • Directory — a du-verified supplier list drops in as a data source

Three containerised services over shared PostgreSQL and Redis. Nothing is tied to one cloud, and the language model sits behind an OpenAI-compatible client — the provider is three environment variables, already exercised against more than one vendor.

09
Where this actually stands

What is built, what is simulated, and what is not built yet.

Built & working

The twin. Three agents against a live model. Consent enforcement. Row-level tenant isolation. Audit trail. Opt-in automatic action. The track-record page. The full API contract.

96 automated tests — 74 platform, 22 AI service.

Simulated

Supplier disruption signals. The prediction logic is real; the feed is seeded. Live carrier and port data is a pilot-stage integration, and is scoped as one rather than implied.

Not built yet

Production authentication — login is a development shim. Outbound email and SMS delivery: intent is recorded, nothing is sent. Deployment to a hosted environment.

A load test at pilot scale — 150 tenants, 3,000 inventory items — returned alert delivery p95 of 234ms and twin reads p95 of 50ms against a five-minute budget. That is sequential latency on a developer laptop, not a concurrency measurement, and the report says so. Re-running it on the deployed environment is a gate before the 150-SME cohort, not after.

10
Non-negotiable must-haves

All three, and how.

Built for rapid scalability

Three independently scalable stateless services, containerised, over shared PostgreSQL and Redis. No per-customer infrastructure.

100% digital integration

Signup, data connection, consent, prediction, recommendation, decision and audit are all in-product. No manual or offline step in the core loop.

Scales to 40,000+ SMEs

Row-level isolation on shared tables rather than a database per customer. Validated at 150 tenants; the next gate is 1,500.
